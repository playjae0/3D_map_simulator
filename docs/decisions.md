# 결정 사항

## 확정

| 항목 | 결정 | 근거 |
|---|---|---|
| 형상 수준 | LOD1: 외곽선을 높이만큼 extrude. 지붕 형상 없음 | 단순 형상으로 도시 스카이라인 표현이 가능하고 데이터로 바로 생성된다 |
| 보여주는 방식 | 카메라 각도·높이를 고정하거나 제한하고, 시야에 들어오는 범위만 그린다. 넓은 범위 조망은 우선순위가 아니다 | 그리는 양을 줄인 여유를 품질에 쓴다 |
| 우선순위 | 범위보다 품질 | 사용자 결정 |
| 메시 저장 방식 | 완성 메시를 저장하지 않는다. 외곽선+높이를 저장하고 기기에서 extrude한다 | 서울 기준 완성 메시 약 430~715MB, 외곽선+높이 약 25~40MB (`measurements.md`) |
| 조명 | AO와 그림자는 PC에서 미리 계산(bake)해 데이터에 저장한다. 해 방향 고정 | 건물이 정적이므로 기기 실행 비용이 거의 없다 |
| 외장 패턴 | 이미지 텍스처 대신 shader에서 층 높이 간격으로 창문 격자 계산. 주용도별 패턴 분리 | 데이터 용량·메모리 증가가 거의 없다 |
| 서버 | 정적 파일 제공만. 렌더링은 기기에서 실시간 | 서버 연산 불필요. 부하는 전송량뿐이며 타일링으로 줄인다 |
| 작업 순서 | 세종으로 전체 파이프라인 검증 → 서울 적용 | 세종 파일이 작아 반복이 빠르고, 같은 국가 데이터셋이라 칼럼 구조가 같을 것으로 예상(확인 필요) |
| 세종 데이터의 역할 | 로직 검증 전용. 화면 품질 판단·시범 지역·고정 시점은 서울에서 정한다 | 세종 파일은 2016년 이후 사용승인 건물이 32동뿐이고 신도시(동 지역) 건물이 대부분 빠져 있다(1단계 점검, 2026-11-24) |
| 테스트 데이터 | 서울 송파구(11710). 서울 원본에서 원천 시군구코드(A23)로 잘라 쓴다(`scripts/clip_region.py`) | 세종은 신도시 건물이 거의 없어 화면 판단이 안 된다(v0.2 사용자 확인, 2026-11-25) |
| 카메라 조작 | 이동·회전·줌. 줌은 카메라 높이 150~1,500m로 제한하고, 높이 400m까지 앙각 22°, 그 위로 1,500m에서 60°까지 높이에 따라 내려다보는 각으로 바뀐다(값은 임시). 기울기를 따로 조작하지 않는다 | 고정 시점만으로는 어디를 보는지 알기 어렵다(v0.2 피드백). 높이·각도를 묶어 그릴 범위를 제한한다 |
| LOD 선택 | 카메라에서 타일 상자까지 거리로 고른다: < 1,000m LOD0, < 2,000m LOD1, < 안개 끝 LOD2. 안개 끝 = max(2,300m, 2.6 × 카메라-주시점 거리). 조금 넓힌 시야 안 타일 + 주시점 900m 안 타일만 불러온다(값은 임시) | 화면에 보이는 크기는 카메라 거리로 정해지므로 줌에 따라 단계가 자동으로 맞춰진다. 시야 밖 타일을 내려 줌아웃해도 그리는 양을 묶는다 |
| 위치 표시 | 미니맵(빌드 때 만든 건물 개요 PNG + 현재 시야·주시점, 탭 이동)과 법정동(리) 라벨(카메라 높이 600m 이상) | 개요 이미지는 미리 만들어 기기 계산이 없다. 라벨 위치는 동별 건물 중심점의 중앙값에 가장 가까운 건물 |
| 높이 정제 규칙 | `data.md`의 "높이 정제 규칙"(임시 확정). 모든 임계값·계수는 서울 확인 후 확정한다 | 1단계 세종 점검 결과 |
| 진행 우선순위 | 기능 구현(정제 → 타일·LOD → 뷰어)을 먼저 한다. 서울 데이터 점검은 그 뒤에 한다 | 사용자 결정 |
| 처리 결과 계약 | `schema.md`의 건물 테이블. 타일·뷰어는 원본 칼럼을 직접 읽지 않는다 | 출처가 바뀌어도(서울, 다른 데이터) 이후 단계를 그대로 쓰기 위해 |
| 타일 파일 형식 | 자체 고정 레이아웃 바이너리(BLDT, `tiles.md`): 헤더 32바이트 + u32/f32/u8 배열, 외곽선+높이만 저장. 500m 타일 × LOD별 파일 + manifest.json | ① 폰에서 파싱이 없다: `ArrayBuffer`를 그대로 TypedArray로 읽어 Worker에서 바로 extrude한다. GeoJSON(문자열 파싱)·MVT(protobuf 디코딩)·FlatGeobuf(flatbuffer 순회)는 디코딩 단계가 따로 있다 ② glTF는 완성 메시라 "메시를 저장하지 않는다" 결정과 맞지 않고 크다 ③ 단점은 자체 형식이라 도구 지원이 없다는 것. 명세를 `tiles.md`에 두고 원본과 왕복 검증했다(세종 LOD0 면적·높이 일치) |
| LOD2 방식 | 블록 병합 대신 작은 저층 건물 생략(면적 100m² 미만이면서 높이 12m 미만) + 박스 | 병합은 묶음의 대표 높이를 정해야 해서 스카이라인이 바뀌고 구현이 무겁다. 생략은 단순하고, 세종 기준 삼각형을 LOD0 대비 79% 줄인다 |
| 외장 패턴 구현 | Lambert 재질에 shader를 덧붙여 창 격자를 계산(이미지 텍스처 없음). 그룹 7개별로 기둥 간격·창 크기·색을 다르게, 층 간격 = 높이 / 층수(타일 v2의 층수). 무늬의 가장 작은 치수가 화면에서 약 4픽셀 아래로 줄면 평균색으로 흐린다. 접지 그늘은 벽 아래 3m를 최대 32% 어둡게(AO 전 임시). `?facade` `?ground`와 화면 패널로 켜고 끈다 | 조명·안개를 기존 재질 그대로 쓰고, 데이터 용량을 늘리지 않는다. 거리별 흐림은 멀리서 격자가 깜빡이는 것을 막는다(헤드리스 측정, `measurements.md`) |
| artifact 배포 빌드 | `npm run build:artifact` → `viewer/dist-artifact/`. 타일은 LOD별 묶음 3개(base64 텍스트) + index.json, Range 요청 우선·미지원이면 묶음 통째 받기. 화면 설정은 URL > 저장값 > 기본값, 화면 패널로도 변경 | artifact 제약: 파일 256개 이하, 쿼리 문자열 미전달, 외부 호스트 차단, 임의 바이너리 형식 미제공(그래서 base64, 용량 약 4/3배). `dist-artifact/`는 git에 올린다(사용자 결정, 세종 타일 포함·출처 표시 화면에 있음) |
| 렌더 단위 지표 | 폰에서 프레임 수를 실측해 거리·시야 기준을 정한다 | 폰 처리 한계(수십만~수백만 삼각형)는 일반 경험치이며 측정값이 아니다 |

## 미정

| 항목 | 상태 |
|---|---|
| 인터랙션 수준 | 정해진 영역 안에서 회전·이동 정도로 가정. 세부 미정 |
| 뷰어 스택 | Three.js + Vite로 최소 뷰어 구현(4단계, `viewer/`). MapLibre는 지도 위 데이터 얹기가 필요해지면 재검토 |
| 카메라·LOD 수치 | 줌 범위(150~1,500m), 앙각 곡선(22°→60°), LOD 거리(1,000/2,000m), 안개 배율은 임시. 송파구 화면과 폰 측정으로 확정. 하늘이 보이려면 앙각이 세로 시야각의 절반(25°)보다 작아야 한다 |
| 배포 형태 | 웹(PWA, 기기 저장소 캐시) 또는 앱. 기기 캐시로 "한 번 받고 계속 사용"은 웹에서도 가능 |
| 시범 지역·고정 시점 | 서울 데이터 확인 후 결정 (세종은 신도시 누락으로 부적합) |

## 하지 않기로 한 것

- 오프라인 고품질 렌더링(영상 프레임 렌더): 폰에서 불가능하고 목적과 다르다
- 서버에서 렌더링해 영상으로 전송하는 방식: 사용자 수만큼 서버 GPU가 필요하다
- 랜드마크 개별 모델링: 투입 대비 효과가 작다
