## 알려진 문제·미확인

- 실제 폰 FPS 미측정. 헤드리스 환경(SwiftShader) 값은 폰 성능 지표가 아니다
- 실제 폰 손가락 조작(핀치·회전) 미확인. 자동 조작으로만 확인
- iOS Safari: 모듈 Worker를 써서 iOS 15 이상이 필요할 것으로 추정(미확인)
- artifact 호스팅의 Range 요청 지원 미확인. 지원하지 않으면 처음에 묶음 전체(세종 약 12MB)를 받는다
- LOD1 박스 면적 과대: 박스가 원래 외곽선의 2배를 넘는 건물이 세종 774동. 줌아웃 화면에서 주변 건물을 덮는 사례 있음(`measurements.md`)
- GIS건물통합정보 공식 필드 명세와 대조하지 못했다(작업 환경에서 V-World 접근 차단). 필드 의미는 데이터 내부 정합성으로 검증
- 세종 파일은 외곽선이 대략 2015년 무렵 상태로 추정(2016년 이후 사용승인 32동). 서울도 같은 문제가 있는지 미확인
- 뷰어 번들 약 561KB(gzip 140KB), 최적화 안 함

## 운영 관련 판단 (미확정, 레이어 추가 시 참고)

- 새 레이어도 건물과 같이 타일로 나누고 거리별 단계를 둔다. 한 번에 받는 양이 보는 범위의 타일로 묶여야 운영 부담이 유지된다
- 바닥을 타일별 이미지로 굽는 방식은 서울 기준 100MB 이상이 늘어날 것으로 추정되어 벡터 방식을 우선 검토한다
- 서울 전체에 레이어를 모두 더한 서버 저장량은 약 100~150MB로 추정(세종 실측 기반 환산, 측정값 아님). 서버 연산은 없고 비용은 전송량에서만 생긴다
